After my [last experiment with `rabbit-hole`](https://github.com/kbutz/rabbit-hole), where I tried to do *everything* inside the browser (deploying cloud infrastructure from a cloud shell), I decided to swing the pendulum back.

For my new research project, **"Web of Senses"** (more on this soon), I returned to the local development patterns I’m most comfortable with. The "Cloud-in-Cloud" friction was interesting, but local tools generally feel more powerful and grounded.

Since I use **Claude Code** almost exclusively at work, I wanted to take this opportunity to properly test drive the **Gemini CLI** on my local machine.

It started with a laugh, and ended with a panic.

## The Setup (and the Meta-Fix)

My first hurdle was purely muscle memory. I went to install Gemini and accidentally grabbed the desktop UI app via Homebrew instead of the CLI tool.

It was a tiny issue, but I found myself in a hilarious "AI loop": I asked **Claude Code** to fix my **Gemini** installation. Claude dutifully provided the correct brew commands, and I was up and running.

We were off to a great start. Or so I thought.

## The Incident: "Please Do Not Commit This"

I was running the Gemini CLI (which defaults to **Gemini 2.5**). I needed to set up my API keys for the project.

I gave the agent explicit, clear guidance: *"Here is the key. Put it in a config file, add that file to .gitignore, and do not commit it."*

Gemini 2.5 acknowledged the instruction... and then immediately committed the hard-coded secret to the repository.

## The Workflow Flaw

Here is where the blame shifts from the AI to the human (me).

To maximize productivity with coding agents, I’ve adopted an **"Agent-First" Workflow**:
1.  Describe the task to the Agent.
2.  Agent writes code, tests it, and pushes it.
3.  Agent opens a Pull Request.
4.  **I review the code in GitHub.**

This workflow is incredibly fast because I’m not constantly stopping to `git diff` or sanity-check every file locally. I treat the Agent like a junior dev who works in the background.

**The Breakdown:** This workflow relies on the assumption that the "push" is safe. By the time I reviewed the code in the Pull Request, the commit history—containing my API key—was already on GitHub.

## The Fallout & The Fix

Five minutes after the push, my inbox exploded. GitHub, Google Cloud, and even third-party security scrapers sent me a dozen alerts: *A valid API key was found in your public repository.*

I had to rotate the key immediately. A classic, painful ritual.

After securing the breach, I dug into the Gemini CLI settings and found a toggle: **"Try Beta Features."** This switches the backend to **Gemini 3**.

I enabled it and re-ran the exact same task.
**Result:** Gemini 3 correctly created the `config.yml`, immediately added it to `.gitignore`, and committed only the safe code.

## The Lesson

This experience reinforced a critical boundary for AI-assisted development.

The "Agent-First" workflow (push now, review later) is fantastic for velocity—until you touch secrets. When dealing with authentication, credentials, or infrastructure security, the "Junior Dev" abstraction breaks down.

You can trust the model to write the logic, but you cannot blindly trust it to respect the git boundary. For now, when an API key is on the clipboard, a human still needs to be the one typing `git push`.
