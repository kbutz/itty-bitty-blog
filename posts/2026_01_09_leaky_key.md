On my [last experiment with `rabbit-hole`](https://github.com/kbutz/rabbit-hole), I stubbornly tried to do *everything* inside the browser including deployment and cloud configuration (using gcloud CLI from Firebase Studio). While fun to figure out, it was ultimately harder than it needed to be.

For a new project that I'm working on, related to trying to build out a visual **"web of senses"** - a visualization of the animal world's "Umwelt," or more importantly how those overlap (or don't overlap) - I knew I needed a different approach. This project would also need to be deployed (if it worked) and would be a bit more complicated. I felt that my learnings from `rabbit-hole` and [`itty-bitty-blog`](https://kbutz.github.io/itty-bitty-blog/2026_01_01_helloworld.html) were enough to warn me (loudly) that I would not be able to make meaningful progress on this new hobby project using exclusively cloud based tools.

Since I use **Claude Code** *a lot* at work, I wanted to take this opportunity to properly test drive the **Gemini CLI** on my local machine.

To get started, I of course asked Claude Code to install Gemini CLI for me.

## The "Please Do Not Commit This" Incident

I was running the Gemini CLI (which defaulted to **Gemini 2.5**). I needed to set up my Gemini API keys for the new project. To do this, I advised Gemini CLI to create a config file that it should **never commit**. 

Gemini 2.5 acknowledged the instruction... and then immediately committed the hard-coded secret to the repository anyway.

## The Workflow Trap

First a call out: if you are dealing with sensitive data and API keys, you shouldn't give your LLM your API key. Have it do the set up for you, then add the key yourself. The way I did this, there is a plaintext API key in my Gemini history somewhere on somebody else's server. Not a suitable workflow for a production workflow.

But anyway, I gave Gemini CLI my API key and told it to add it to my config file for me. 

My workflow here is such that I only review the code *in Github* in the Pull Request. I'm not opening an IDE to review the code locally, ever. This really isn't safe whe you're dealing with API keys - it was really important that I review the diff before it was pushed to Github. Instead, I reviewed it in Github... where I saw the API key...

## The Fallout & The Fix

Five minutes later, my inbox lit up. I had a dozen emails from GitHub, Google, and even third-party security scrapers alerting me that an API key was found in my public repo.

At this point, I dug into the Gemini CLI settings and found a toggle I hadn't noticed before: **"Try Beta Features."** This switches the backend to **Gemini 3**.

I enabled it, rotated my keys, and re-ran the exact same task. Gemini 3 correctly created the `config.yml`, immediately added it to `.gitignore`, and committed only the safe code.

## Retrospective

In the end, this was a good reminder of the limits of our new AI workflows.

The "Agent-First" flow is fantastic for velocity, but it relies on trust. When you're dealing with secrets, that trust needs to be verified *before* the push.

You can let the agents do the heavy lifting, but for now, when there's an API key on the clipboard, a human still needs to be the one sane-checking the `git status` before hitting send.
